# SYNAPSE WEB — ARCHITECTURE AUDIT (Phase A)

**Scope of this document:** audit only. No implementation code was written. This is the sole deliverable for Phase A, per explicit instruction to stop and report before Phase B.

---

## 1. Executive Summary

**There is no standalone "Synapse Web" application in this repository.** This repository (`synapse`, `package.json`) is a single-purpose Electron **desktop** application. Searched exhaustively for a separate web codebase (`next.config`, `vite.config`, a `web/` directory, React/Next/Express/database/ORM/auth dependencies in `package.json`) — none exist.

The closest thing to "a basic web agent" is the **Web Companion**: a small HTTP+WebSocket server (`mobile-server/server.js`, 1090 lines) that the desktop app starts on port 7823, serving two *different* static web surfaces:

1. **`mobile.html`** (1441 lines, served at `/`) — a phone-oriented remote control: resume/JD upload forms, live transcript viewing, auto-answer toggle, typing-speed control.
2. **`dashboard/*`** — a separate, visually distinct "3D Sci-Fi Management Core" ops console (service health tiles, live transcript "observatory," log viewer, service restart buttons) with its own login page and a decorative Three.js backdrop.

There's also a third file, **`mobile-legacy.html`** (852 lines) — confirmed **dead code**, not routed anywhere.

**The critical architectural fact this audit needs to state plainly:** both existing surfaces are *remote controls for the running desktop app's local services*, not an independent interview-answering product. They have no database, no per-user accounts, no independent AI orchestration loop, and cannot function without the Electron desktop process running on the same machine. This is not a criticism of the existing code — it does its actual job (remote monitoring/control) well — it's a statement that **the product described in the Phase 1 prompt does not yet exist in any form, and building it means a new, independent, standalone application, not a redesign of the Web Companion.**

## 2. Current Architecture (What Actually Exists)

### 2.1 Web Companion server (`src/main-process/features/mobile-server/server.js`)
Plain Node `http` + `ws` server (no Express/Fastify/framework), constructed and started from `start-application.js`, listening on `0.0.0.0:7823`.

**Routes actually served:**
| Route | Purpose |
|---|---|
| `POST /api/login` | Exchanges a TOTP passcode (or resumed bearer token) for a session token |
| `GET /api/status` | Live health of local services (Whisper, Ollama, latency, BlackHole) |
| `GET/POST /api/context` | Read/merge-write the interview brief (role, company, resume text, JD text, etc.) |
| `POST /api/jd` | Save + re-index JD text |
| `POST /api/resume` | Upload (PDF/text) + parse + re-index resume |
| `POST /api/restart-service` | Restart Whisper/Ollama |
| `POST /api/toggle-autopilot`, `POST /api/set-typing-speed` | Remote control of desktop behaviors |
| `POST /api/recall` | Keyword search over resume/JD (the retrieval logic audited/upgraded in earlier phases) |
| `GET /api/logs` | Tail recent logs |
| `/`, `/dashboard/*` | Static HTML/CSS/JS for the two UIs above |

**Auth:** a single shared TOTP secret generated by `totp-auth.js`, displayed in the desktop app's tray menu. Anyone who can read that 6-digit code (i.e., is standing near the Mac) gets a session token. **This is device-proximity auth, not user authentication** — there is no user table, no per-user isolation, no concept of multiple accounts.

**Persistence:** the "interview brief" (role/company/resume/JD text + Phase 9's `structuredProfile`) lives in one JSON file on the local filesystem (`interview-context.js`, `<userData>/cache/interview-context.json`). There is no database.

### 2.2 The two frontends
- **`mobile.html`**: single static HTML file, vanilla JS, no build step, no component framework, no state management library. Functional but visually basic — plain forms and text, no design system.
- **`dashboard/*`**: a second, separate static-file frontend with a decorative sci-fi visual theme (glowing "holo-cards," Three.js starfield), oriented entirely around *service health monitoring*, not interview content. Its own small `login.html`/`context.html`/`app.js`. This is a genuinely different product surface from `mobile.html` and shares no components with it.

### 2.3 AI pipeline (desktop-side, NOT web-accessible independently)
All AI generation (`gemini-service.js`, `prompts.js`) runs **inside the Electron main process**, using a Gemini API key entered through the desktop Settings UI and held in that process's memory/local state — never exposed to any browser. The Web Companion never calls Gemini directly; it only reads/writes the *context* that the desktop app's own pipeline later uses when the user triggers an answer *from the desktop app itself*. **There is currently no way to ask a question and get an AI-generated answer from a browser at all** — the phone UI is for prep/monitoring, not for conducting an interview through the browser.

### 2.4 Reusable intelligence logic (the genuinely good news)
Several modules built across this project's development are **pure, framework-agnostic, dependency-free JavaScript** with zero Electron/DOM coupling — real assets for a web build:

| Module | What it does | Reuse viability |
|---|---|---|
| `src/services/context/candidate-profile.js` | Structured resume parsing → `CandidateProfile` (education/experience/projects/skills/achievements/certifications), with per-technology experience-status grounding (`VERIFIED_EXPERIENCE`/`PROJECT_EXPERIENCE`/`WORKED_WITH`) | **High** — pure Node, no filesystem/Electron dependency beyond the resume-text string it's given |
| `src/services/context/jd-profile.js` | Structured JD parsing (responsibilities/required/preferred skills) + candidate↔JD technology matching | **High** — same, pure |
| `src/services/ai/resume-parser.js` | PDF/text → section-tagged bullets | **High** — pure Node (`pdf-parse` + regex), no Electron |
| `src/windows/assistant/renderer/features/auto-answer/question-relation.js` | Deterministic follow-up/comparison/refinement/correction classification | **High** — pure ES module, no DOM |
| `.../auto-answer/semantic-reference.js` | Pronoun/ellipsis resolution ("How does that scale?" → "How does PostgreSQL scale?") | **High** — pure |
| `.../auto-answer/conversation-tracker.js` | Conversational state machine tying the above together | **High** — pure, no DOM calls found |
| `src/services/ai/prompts.js` | The actual answer-generation prompt: natural-voice instructions, evidence hierarchy, JD-vs-experience grounding rules (the product of many rounds of refinement this session) | **Medium** — the *prompt text/logic* is pure and portable; it currently reads from `interview-context.js` (a local-file store) and is wired to Gemini specifically |
| `src/services/system-health.js` | BlackHole/audio-routing checks | **None** — desktop-audio-specific, not applicable to a web build |

This is a meaningful head start: the hardest, most-iterated-on part of "sounding like a real candidate, not a chatbot" and "resolving follow-ups without restarting" **already exists and works** (117+ tests across this session confirm it). A web build should **reuse this logic**, not rebuild it.

## 4. Data Flow (Current, Web Companion Only)

```
Phone/browser (mobile.html)
    ↓ POST /api/resume (PDF or text)
mobile-server/server.js
    ↓ resume-parser.js (extract sections)
    ↓ interview-context.js.save()
        ↓ candidate-profile.js (Phase 9 — structured profile, computed synchronously)
    ↓ writes ONE JSON file to local disk (<userData>/cache/interview-context.json)

[Separately, later, inside the DESKTOP app's own renderer:]
Host audio → AssemblyAI → conversation-tracker.js → prompts.js → gemini-service.js → answer
    (this path never touches the Web Companion or a browser at all)
```

There is no path today where a question typed/spoken into a browser produces an AI-generated answer *in that browser*.

## 5. Technical Debt

- **`mobile-legacy.html`** — dead code, unrouted. Should be deleted when this area is next touched (not this phase, since it costs nothing to leave and deleting is not part of Phase A).
- **Single shared local JSON file for context** — cannot support multiple sessions or multiple users by construction; would need to become real per-session, per-user records before Phase F (Session system) is possible.
- **Two unrelated, non-componentized frontends** (`mobile.html`, `dashboard/*`) sharing zero UI code — not a foundation to "redesign," effectively a fresh build either way.
- **`prompts.js` is coupled to `interview-context.js`'s local-file `load()`** — a web backend needs this fed from a real per-user database record instead; the prompt-construction logic itself doesn't need to change, only what feeds it.

## 6. Security Risks (Current Web Companion, for awareness — not this phase's job to fix)
- Single shared passcode = **anyone with LAN access and the current code can control the desktop app** (by design, for a *local* companion — but this pattern is **not acceptable for a real multi-user web deployment** and must not be carried forward).
- No rate limiting beyond login (`/api/resume`, `/api/jd` etc. have size caps but not per-IP throttling).
- Server binds `0.0.0.0` — deliberate (LAN reachability for a phone), again inappropriate for a public web deployment without a real reverse-proxy/auth layer in front.

## 7. Performance Risks
Not yet applicable — no independent AI request path exists in the web surface to measure. This becomes relevant starting Phase C/D.

## 8. Recommended Architecture

**Build Synapse Web as a new, independent, standalone application — not a modification of the existing Electron app or Web Companion.** Per the explicit instruction ("treat Desktop Synapse and Synapse Web as separate surfaces... do not modify desktop functionality"), and given the Web Companion's architecture is fundamentally a local remote-control (single shared secret, one local file, no DB), it cannot become a real multi-user SaaS product through incremental changes — it would need to be rebuilt regardless.

**Recommended structure:**
```
/ (existing repo root — untouched, desktop app stays exactly as-is)
/web/                          ← new, independent application
  /web/app or /web/src         ← frontend
  /web/server (or /web/api)    ← backend
  /web/shared-intelligence/    ← candidate-profile.js, jd-profile.js, resume-parser.js,
                                  question-relation.js, semantic-reference.js,
                                  conversation-tracker.js — COPIED from the desktop app
                                  (not modified in place there), each file's origin
                                  noted in a header comment, kept in sync deliberately
                                  rather than silently drifting
```

Copying (not sharing a live path into `src/`) is the safer choice here: it guarantees zero risk of an ill-considered web-side change ever affecting the desktop app, at the cost of needing to deliberately re-sync if either side improves this logic later. A true monorepo/shared-package extraction is possible as a *later*, separately-scoped refactor once the web app's actual needs are known — not a Phase A/B decision.

**What genuinely needs to be built new:** auth (real user accounts), a database (sessions, candidate profiles, JD records, conversation history — one JSON file cannot serve multiple users), company-research integration (does not exist anywhere today, needs a real external data source), the entire premium UI, session management, prep dashboard, mock-interview mode, and a new AI-orchestration path that runs server-side (never exposing the Gemini key to the browser, per the explicit security requirement).

## 9. Files That Should NOT Be Touched

Every file under the existing `src/` tree, `scripts/`, `tests/`, `package.json` — **the entire current repository** — must remain untouched by this work, with one narrow exception: reading from it to copy the reusable pure-logic modules listed in §2.4 into the new `web/` tree. No existing file gets edited in place. This preserves everything this session has already built and verified (117+ tests, the audio/latency work, Phase 2-13's answer-quality work) with zero risk.

Recommended sequencing stays as specified (A→J), with the same discipline this whole project has used throughout: audit/measure before each phase, real tests before claiming anything works, no fabricated data, explicit stop-and-report after each phase.
